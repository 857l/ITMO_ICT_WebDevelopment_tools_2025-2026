## Задача 1. threading vs multiprocessing vs async на CPU-bound задаче

Считаем сумму чисел от 1 до N. В коде `N = 100_000_000` — честный прогон
на 10^13, как в общей формулировке задания, физически не успевает
завершиться на чистом Python за разумное время; сравнительные выводы
от масштаба N не меняются, так как все три подхода прогоняются на
одинаковом N.

```
task1/
├── sum_threading.py        # run_threading(n, num_threads=4) -> (сумма, время)
├── sum_multiprocessing.py  # run_multiprocessing(n, num_processes=4) -> (сумма, время)
├── sum_async.py            # run_async(n, num_tasks=4) -> (сумма, время)
└── benchmark.py            # прогоняет все три и печатает сравнительную таблицу
```

Запуск:

```powershell
cd task1
python benchmark.py
```

### Результаты замеров (N = 100 000 000)

```

Метод                | Время (сек)
----------------------------------------
Потоки               | 3.3454
Процессы             | 1.1203
Асинхронность        | 6.1162
----------------------------------------
```

Сумма во всех трёх подходах совпала: `5000000050000000`.

### Объяснение

| Подход | Модуль | Параллелизм | Когда эффективен |
|---|---|---|---|
| threading | `threading` | Конкурентность в одном процессе, ограничена GIL | I/O-bound задачи |
| multiprocessing | `multiprocessing` | Настоящий параллелизм, свой GIL на процесс | CPU-bound задачи |
| async | `asyncio` | Кооперативная многозадачность в одном потоке | I/O-bound с большим числом ожиданий |

Результат полностью соответствует теории:

- **`multiprocessing` оказался самым быстрым (1.12с)** — единственный
  подход из трёх, дающий настоящий параллелизм на CPU в CPython: у
  каждого процесса свой интерпретатор и свой GIL, поэтому вычисления
  реально идут на разных ядрах одновременно.
- **`threading` (3.35с)** — заметно медленнее процессов: GIL не даёт
  потокам выполнять байткод Python параллельно на CPU-bound задаче,
  поэтому выигрыша от многопоточности здесь нет, только накладные
  расходы на переключение контекста.
- **`async` (6.12с)** — самый медленный: корутины выполняются
  кооперативно в одном потоке, `await asyncio.sleep(0)` лишь передаёт
  управление между ними (без этого одна корутина заняла бы event loop
  целиком до своего завершения), но не даёт параллелизма на CPU и
  добавляет дополнительные накладные расходы на переключения.

## Задача 2. Параллельный парсинг с сохранением в PostgreSQL

Качаем несколько страниц, вытаскиваем `<title>`, сохраняем в таблицу
`scrapedpage` (модель `ScrapedPage` в `task2/models.py`, SQLModel).
У каждой записи есть поле `approach` (`threading` / `multiprocessing` /
`async`), которое показывает, каким методом она была получена —
удобно проверять результат прямо в БД без сопоставления с логами.

```
task2/
├── models.py                    # SQLModel: ScrapedPage(url, title, approach), init_db(), get_session()
├── scrape_threading.py          # run_threading(urls) -> время
├── scrape_multiprocessing.py    # run_multiprocessing(urls) -> время
├── scrape_async.py              # run_async(urls) -> время (aiohttp)
├── benchmark.py                 # инициализирует БД, прогоняет все три, печатает таблицу
└── .env                         # DB_URL (не публикуется в репозиторий)
```

Запуск:

```powershell
cd task2
python benchmark.py
```

Проверить результат в БД (через pgAdmin Query Tool или psql):

```sql
SELECT approach, count(*) FROM scrapedpage GROUP BY approach;
SELECT id, url, title, approach FROM scrapedpage ORDER BY approach, id;
```

### Важный нюанс: multiprocessing + SQLAlchemy engine

Движок SQLAlchemy (`engine` в `models.py`) создаётся один раз при
импорте модуля. Если создать `multiprocessing.Pool` уже после того, как
через этот `engine` было открыто соединение, дочерние процессы (созданные
через `fork`/`spawn`) могут унаследовать или помешать соединениям
родителя — это приводит к ошибкам вида `SSL error` / `connection closed
unexpectedly`. Решение в `scrape_multiprocessing.py`: `engine.dispose()`
вызывается в родителе **до** создания пула процессов (чтобы нечего было
наследовать), и в каждом дочернем процессе через `initializer` (чтобы
точно открыть свежее соединение).

### Объяснение

Задача 2 — **I/O-bound** (время уходит на ожидание сети/БД), поэтому
картина отличается от задачи 1:

- **`async` стабильно самый быстрый** (0.52с в этом прогоне) — не
  требует создания потоков/процессов, одна корутина на URL, event loop
  просто переключается между ожидающими соединениями без накладных
  расходов ОС.
- **`threading` (обычно 1–2с, иногда больше из-за медленных сайтов)** —
  во время сетевого ожидания GIL освобождается, поэтому потоки дают
  реальное ускорение относительно последовательного парсинга, хотя
  создание потоков даёт небольшие накладные расходы.
- **`multiprocessing` (2.20с)** — тоже ускоряет относительно
  последовательного варианта, но создание 4 процессов и открытие для
  каждого отдельного соединения с БД — заметно более тяжёлая операция,
  чем создание потока или корутины, поэтому на такой лёгкой задаче
  (всего 7 URL) `multiprocessing` проигрывает `threading` и `async`.

## Общий вывод

- Для **CPU-bound** задач (задача 1) выигрывает `multiprocessing` —
  единственный подход из трёх, дающий настоящий параллелизм на CPU в
  CPython. Замеры это подтвердили: 1.12с против 3.35с (`threading`) и
  6.12с (`async`).
- Для **I/O-bound** задач (задача 2) `async` и `threading` оказываются
  эффективнее и легковеснее `multiprocessing`, так как не требуют
  создания отдельных процессов ради ожидания сети. Замеры это тоже
  подтвердили: `async` — 0.52с, `multiprocessing` — 2.20с.
- Причина в GIL: он не даёт потокам выполнять байткод Python параллельно,
  но освобождается на время системных вызовов (сеть, диск) — поэтому
  `threading` полезен именно для I/O-bound нагрузки, а не для CPU-bound.
